## 2. 赛题目标

参赛者需要设计并打包一个能够自主搜索集合通信调度方案的 AI Agent。平台将向 Agent 提供任务和拓扑约束，Agent 读取输入、分析拓扑、构造通信计划，并提交可回放验证的 solution。

题目的核心不是复述某一种固定算法，而是在不同规模、不同资源瓶颈和不同拓扑下，自动找到满足正确性约束且尽可能快的调度方案。正式实例会更换参数，不能依赖固定 rank 数、固定路径或预存答案。

本题包含两个算子：

| 算子                 | 初始状态                 | 最终状态                                | 正确性目标                          |
| ------------------ | -------------------- | ----------------------------------- | ------------------------------ |
| **AllGather（全收集）** | 每个 rank 持有自己的数据分片    | 每个 rank 都持有全部 rank 的分片              | 符号 Replay 验证分片身份、初始归属与最终全集     |
| **AllReduce（全规约）** | 每个 rank 持有自己的梯度/数据分片 | 每个 rank 都持有所有 rank 数据按题目规定逐元素规约后的结果 | 符号 Replay 验证各规约槽位覆盖全部贡献者且无重复贡献 |

设参与 rank 数为 `N`，每个 rank 的原始数据量为 `M`（字节），均为任务变量。AllGather 每个 rank 最终新增 `(N-1)×M` 数据；AllReduce 通常包含 ReduceScatter（RS）和 AllGather（AG）两个阶段，数据在规约过程中会合并，不能把它当成简单复制。

|                | **AllGather**        | **AllReduce**                     |
| -------------- | -------------------- | --------------------------------- |
| 起点（每 rank）     | 持有 1 个原始数据分片         | 持有 1 份梯度/数据分片                     |
| 最终目标（每 rank）   | 收齐全部 `N` 个分片，顺序和归属正确 | 获得全部 `N` 份数据逐元素规约后的结果             |
| 当前判题依据          | 分片身份、初始归属、逐轮状态和最终全集       | 各槽位的规约贡献者集合、无重复贡献和最终覆盖               |
| 每 rank 新增/线上流量 | `(N-1)×M`            | 约 `2×(N-1)/N×M`，取决于 RS/AG 方案      |
| 数据演化           | 只增不减，持有量可逐轮扩展        | RS 阶段规约压缩，AG 阶段将规约分片传播            |
| 典型基线轮数         | 按拓扑层级递归加倍，各层轮数之和     | RS 与 AG 两段通常对称，约为 AllGather 的 2 倍 |
| 主要优化方向         | 带宽池编排、路径和分片并发        | 规约贡献管理、轮次压缩和流水重叠                  |

上表只是理解算法的通用参照。正式任务的轮数上限、切分候选、边带宽和共享资源均由任务/拓扑输入给出，Agent 必须逐题计算。

当前输入不包含真实张量和数值金标，判题器验证的是调度与规约贡献语义，不进行真实数据的逐元素运算或 checksum 校验，也不要求参赛者提交自报 checksum 作为正确性证据。如正式版增加数值验证，组委会将同步发布数据、数值规则和对应 Replay 版本。

## 3. 四类正式拓扑

四类拓扑共用同一套任务和 solution 外层协议，但节点分组、可用路径、共享资源和带宽瓶颈不同。所有参数必须从拓扑输入文件读取，不能根据拓扑名称自行补全连接、带宽或交换机数量。具体参数见拓扑与输出规范文档。

### 3.1 Topology 1：CloudMatrix

CloudMatrix 是分层交换网络。专家资料中的示例为 128 个 rank、224 个交换节点：

- 第一层包含 16 个局部 Node，每个 Node 有 7 台 L1 交换机，命名形如 `L1-N0-S0`；
- 第二层包含 7 个平面，每个平面有 16 台 L2 交换机，命名形如 `L2-P0-S0`；
- 典型跨 Node 路径为 `rank → L1 → L2 → L1 → rank`；
- 边带宽、方向、共享资源和可用路径以输入文件逐边定义为准。

该拓扑的主要挑战是局部域入口、平面共享容量、交换机跳数和跨域流量编排。输入中未声明的 rank-交换机或交换机-交换机直连不得使用。

### 3.2 Topology 2：1D Full-Mesh + Clos

该拓扑为两机柜、每柜 64 卡的 128 rank 实例，每个 Node 包含 8 个 rank：

- Node 内 8 个 rank 两两 Full Mesh；
- 每个机柜有 8 台共享 L1 交换机，命名形如 `L1-C0-S0`；
- 两个机柜之间通过 4 台共享 L2 Clos 交换机互联，命名形如 `L2-P0-S0`；
- Node 内、L1、L2 的边关系和容量必须严格读取输入文件，不能把局部 Mesh 推断为任意两点直连。

该拓扑适合考察局部 Full Mesh 与机柜级 Clos 的分层调度、共享交换机争用和跨柜流量控制。资料中的带宽是赛题输入的容量设定；背景材料中的厂商或论文参数不是额外的判题依据。

### 3.3 Topology 3：2D Full-Mesh + Clos

该拓扑包含 128 个 NPU，分为 2 个机柜；每柜 8 个 Node，每个 Node 8 个 NPU。rank 编号按以下规则解释：

```text
rank = 机柜号 × 64 + 柜内 Node 号 × 8 + 槽位号
```

柜内连接为二维 Full Mesh：

- 同一 Node 内，不同槽位的 NPU 两两直连；
- 同一机柜内，不同 Node 的相同槽位两两直连；
- 这不是 64 个 NPU 的整体 Full Mesh。

全局有 8 台 UB Switch，命名形如 `L1-P0-S0`，每台可按输入文件直接连接全部 128 个 NPU；交换机之间没有输入文件未声明的其他链路。示例资料中柜内直连和 NPU-交换机边使用不同的单向容量，实际数值和联合容量约束以正式输入文件为准。

### 3.4 Topology 4：GB200 NVL72 缩放实例

该拓扑是 GB200 NVL72 风格的两柜缩放实例，共 144 个 GPU/rank，每柜 72 个 GPU：

- 每柜 18 个 Compute Tray，每个 Tray 4 个 GPU；
- 每柜 18 个 NVSwitch ASIC，命名为 `NV-C0-S0` 至 `NV-C0-S17`（另一柜为 `C1`）；
- 每个 GPU 连接本柜 18 个 NVSwitch；示例中 GPU-NVSwitch 边单向容量为 50 GB/s，每 GPU 柜内总单向容量为 900 GB/s；
- 每柜通过 4 条 rail 连接到 4 个 Leaf，8 个 Leaf 命名为 `Leaf-C0-R0` 至 `Leaf-C1-R3`；
- 两柜通过 9 个共享 Spine 互联，命名为 `L2-P0-S0` 至 `L2-P0-S8`；
- 专家实例合计 53 个交换芯片/交换机节点和 2808 条逻辑双向 edge，最终以输入文件为准。

典型路径为：

```text
柜内：GPU → 本柜 NVSwitch → GPU
跨柜：GPU → Leaf → Spine → Leaf → GPU
```

输入中没有 GPU-GPU 直连、NVSwitch-NVSwitch 直连或跨柜 NVLink 直连时，Agent 不得自行使用这些路径。`bw` 表示单方向容量；双向通信可以同时使用两个方向的容量，但不能把整柜总带宽当成单个 GPU 的链路带宽。

### 3.5 拓扑参数化和数据源优先级

正式考题不限于上述示例规模。不同实例可能改变 rank 数、Node/机柜数量、交换节点数量、边带宽、方向性、共享资源、切分候选和轮数上限。参赛者不得根据 `CloudMatrix`、`Clos`、`2D` 或 `NVLink` 名称猜测参数。

每个实例的数据源按以下优先级理解：

1. **任务输入**：算子、参与 rank、数据量、chunk/split、轮数、通信开关和任务级约束；
2. **拓扑输入**：rank/NPU/GPU、交换节点、Node/机柜/坐标分组、边、带宽、方向、启动与交换机处理开销、共享资源及合法路径；
3. **平台 Replay 返回**：方案是否可行、违规原因、逐轮耗时和总耗时；
4. **平台提供的基线和金标**：用于性能比较和正确性校验，不应被写入参赛者镜像作为隐藏答案。

当公开文件中的说明文字与正式字段存在差异时，以冻结版 Schema 和更具体的边/资源字段为准。输入没有声明的边、路径、容量或交换机缓存能力均视为不存在。

## 4. Agent 核心功能要求

参赛开发的 AI Agent 需具备以下核心功能，围绕“集群集合通信调度搜索”实现全流程自动化处理：

1. **任务解析与前置校验**：读入 CC 任务输入（算子类型、rank 列表、拓扑分组、数据块大小、split 策略、通信约束）与配套拓扑约束文件，自动完成 Schema 与语义校验。至少检查 rank 数量和编号、参与集合、rank 与 switch 不相交、初始分片、切分对齐、边和共享资源引用、方向性、轮数限制等；对 CloudMatrix、机柜/Node 分组、2D 坐标或 NVLink/NVSwitch 层级，还应检查输入文件声明的覆盖关系（例如分组恰好覆盖每个 rank，且不跨越输入声明的域边界）。非法任务须主动拒绝并说明原因。
2. **算子目标识别**：本赛题包含 **AllGather** 与 **AllReduce** 两类算子，Agent 须先识别算子类型及其最终目标，再选择匹配的调度构造策略。不能把 AllReduce 当成简单复制，也不能把 AllGather 的分片身份丢失。
3. **调度方案构造**：在全部通信约束下生成通信调度方案，包括每轮 transfer、动作、分片和合法路径。算法不限（环、树、递归加倍、分层、分维交换、混合网格、AlltoAll、分块流水均可），可自主决定 split 切分、rank 映射、路径和绕路策略。
4. **仿真验证与迭代闭环**：调用平台 Replay/仿真接口验证方案的正确性和完成时间，定位约束违反、资源冲突或性能瓶颈，迭代改进直至收敛或配额耗尽。鼓励多方向并行探索，例如不同拓扑映射、不同基数、流水线重叠、ReduceScatter/AllGather 分块流水等。
5. **结果输出**：对每个任务实例输出完整调度方案、Replay 需要的性能指标和简短策略说明，并通过平台接口提交。字段级格式以随题发布的输入输出规范为准。

### 4.1 任务解析与前置校验

Agent 应读取任务文件和配套拓扑文件，识别算子、rank、数据量、切分候选、轮数限制、交换节点、边、方向性、带宽、启动/处理开销和共享资源。发现非法或不完整任务时，应返回清晰的拒绝原因，不应静默补全为任意直连或无限带宽。

### 4.2 调度构造、Replay 和搜索闭环

每个 transfer 只能读取该轮开始时源 rank 已经持有的内容；`copy` 只复制已有分片，`reduce` 只进行题目允许的规约；不能依赖输入未声明的边、交换机或跨轮缓存；不能超过任务规定的轮数和切分约束。

推荐的执行闭环为：

```text
解析与校验 → 生成候选 → Replay → 定位瓶颈/违规 → 调整映射、切分或轮次 → 再 Replay
```

AllReduce 的 ReduceScatter 阶段必须保证贡献者集合不重复，避免同一原始数据被重复规约；后续 AllGather 阶段再将规约分片传播到所有 rank。搜索可并行比较多种候选，但必须在平台规定的调用配额和时间限制内完成。

### 4.3 Solution 输出

每个实例应提交一份完整 solution，包括初始分片和目标分片说明、逐轮传输计划、算子动作、路径标识、性能指标和简短策略说明。AllGather 使用 `copy` 传输；AllReduce 的规约阶段使用 `reduce`，传播阶段使用 `copy`。

字段名称、类型、`route_id` 格式、`final_chunks` 表达方式和 metrics 单位均以随题发布的《拓扑输入与 Agent 输入输出规范》及示例文件为准，不要根据本说明自行发明兼容字段。

格式示例中的 `...` 仅表示文档省略，实际提交必须包含完整的 `chunks`、`initial_possession`、`final_chunks` 和调度内容。初始分片只能来自任务规定的原始归属，不能预填其他 rank 的数据；算子和已提供的任务/实例 ID 必须与当前任务一致。切分数必须满足任务候选及对齐约束，不能通过少列 rank 或分片缩小目标。

在当前符号 Replay 中，AllReduce 的聚合分片以“槽位 + 贡献者集合”标识。例如 `r0_c0+r1_c0` 表示两个贡献已经规约为一个槽位的结果，源 rank 必须实际持有这个完整集合；`c0_sum` 只能表示全部参与 rank 的该槽位已经规约完成。传播阶段的 `copy` 只能发送完成规约的分片，最终每个 rank 都须覆盖所有槽位及全部贡献者。

## 5. 通信约束与正确性

以下是所有实例的核心硬约束；若正式输入对某项给出更具体的限制，以正式输入为准：

1. **持有性**：rank 只能发送本轮开始时已经持有的分片或规约结果；同轮接收结果不能在同轮再次被 rank 发送。
2. **接收唯一性**：同一目标 rank 对同一逻辑分片只能按题目允许的方式接收一次，不能重复注入相同分片。
3. **发送唯一性**：同一 `(chunk, src, dst)` 组合不能重复发送。AllReduce 中的逻辑分片身份包含槽位及当前贡献者集合，不能通过改变聚合表达式的书写顺序规避检查。
4. **交换机无跨轮存储**：交换机只在当前路径上转发，不能把数据留到下一轮，也不能把交换机当作额外计算 rank。
5. **路径合法性**：路径端点必须与 transfer 的 `src`、`dst` 一致，路径无重复节点，并且由输入声明的有向或双向边组成；中间节点只能是声明的交换机。需要 rank 中继时，须让数据先到达该 rank，再在后续轮次发送。沿途每条边及输入明确声明的共享资源均按其容量和方向计费；不能根据交换机名称补全未声明的内部容量。
6. **轮数和切分**：总轮数不得超过任务上限，切分数量和对齐必须来自输入文件允许的候选。
7. **AllReduce 规约语义**：规约必须覆盖每个原始贡献且不能重复计入；同轮多个发送者对同一目标槽位的贡献也必须相互不重叠。最终所有 rank 的各槽位贡献者集合均为参与 rank 全集。

## 6. 计时口径

本题区分两种时间：**通信方案 Replay 耗时**用于评价输出方案完成集合通信的效率，单位为微秒；**Agent 求解时间**用于评价从任务下发到最终方案返回的速度，单位为秒。前者不是 Agent 的程序运行时间，也不表示其求解算法的时间复杂度。

### 6.1 通信方案 Replay 耗时

通信参数由拓扑输入或任务输入提供。当前离线 Replay 的计时规则如下，正式版本将在赛前冻结。设逻辑传输 `t` 的有效数据量为 `B_t`（字节），经过 `h_t` 个交换机；链路 `bw` 转换为字节/秒。单次路径耗时为：

```text
传输耗时 = communication_startup_time_us
         + 交换机跳数 × switch_processing_overhead_us
         + 10^6 × sum(B_t / bw_e)，e 为路径各有向链路
```

启动和交换机开销均以微秒计。启动开销不按全网设备数量累加，交换机开销按各路径实际经过的交换机数计算。AllGather 按发送的原始分片字节量计费；AllReduce 规约后同一槽位的数据大小仍是一个 chunk，不乘以原始贡献者数量。

同轮共享链路的流量需要合并，不能只计算孤立路径时间。设有向边 `e` 上的本轮负载为 `L_e = sum(B_t)`，求和范围为经过该边的传输；定义：

```text
本轮最大开销 A = max_t(communication_startup_time_us
                         + h_t × switch_processing_overhead_us)
有向边忙碌时间 D_e = 10^6 × L_e / bw_e
声明共享资源的忙碌时间 D_r = 10^6 × 该资源计费负载 / 该资源容量
本轮耗时 = max(max_t(传输耗时_t), A + max(max_e(D_e), max_r(D_r)))
总耗时 = sum(各轮耗时)
```

未声明额外共享资源时，资源项取 0；空轮耗时为 0。双向边的两个方向分别统计负载；如输入明确将多个方向或链路绑定到同一个共享资源，还须按该资源定义合并计费。当前四类专家拓扑主要声明边和带宽，未声明的交换机内部联合容量不额外推断。

链路单位 `GB/s`、`MB/s` 使用十进制换算；任务中的 `data_size.per_rank_bytes` 为精确字节量。专家拓扑中的数据量字符串 `1MB` 沿用 `1,048,576` 字节的示例约定，实际任务优先使用整数字节字段。solution 的 `metrics.total_time`、`metrics.round_times` 按示例以秒表达；平台 Replay 报告和通信性能评分时间以微秒表达，自报 metrics 不替代 Replay 结果，也不能作为 Agent 求解时间。

以上是统一的离线模型耗时，不是实机测速结果或完整事件级仿真。正式评测中参赛方案和官方基线必须使用同一冻结版本；调整计时规则或资源定义时，组委会须同步重新标定基线和评分参数。平台 Replay 返回的耗时是通信性能项的判分依据。

### 6.2 Agent 求解时间

平台在 Agent 通过健康检查、计算资源就绪后，使用宿主机单调时钟统一计时：从开始向 Agent 发送当前实例的完整任务请求，到完整接收本次最终方案响应为止，记为 `t_i`，单位为秒。计时包含请求与响应传输、输入解析、模型调用、搜索、工具执行、Agent 求解期间调用 Replay 的等待与执行、内部验证及结果序列化；不包含评测排队、镜像导入、容器启动，以及最终响应收齐后由平台进行的独立判题和评分。

一次实例求解以一次最终响应为提交依据。Agent 可在内部生成和验证多个候选，但计时不会因重试、重新规划或调用工具而重置，最终应返回自己保留的最好可行方案。首个候选生成时间、首 Token 时间及 Agent 自报耗时均不代替平台记录。当前协议不接收中间候选作为正式提交，容器内文件或日志中的候选也不算已提交；未在截止时间内完整返回最终方案，按超时失败处理。

所有队伍使用相同的 CPU、内存、加速设备配置（如提供）、并发上限，以及模型和 Replay 服务配额。同一实例的计时与阈值对所有队伍一致；平台控制共享服务并发干扰。仅对可核实的平台故障，由组委会按统一重测规则作废受影响记录并重测，不从多次执行中任意选取最快结果。参赛者自身算法失败、崩溃或超时不属于平台故障。

## 7. 打榜用例和资源限制

评测包括公开调试用例和不公开的正式打榜用例。随题资料包中的 `agentcc_solution_example.json` 和 `agentcc_allreduce_solution_example.json` 是 AllGather 与 AllReduce 的 solution 格式示例，不是两个完整的公开调试实例。公开调试实例将另行发布，数量、任务输入及配套拓扑以赛前公告为准；公开调试成绩不计入最终排名。

正式打榜集共 **16 个实例**，四类拓扑各 4 个，每类拓扑包含 AllGather 2 个、AllReduce 2 个，具体分配如下：

| 拓扑 | AllGather | AllReduce | 合计 |
| --- | ---: | ---: | ---: |
| CloudMatrix | 2 | 2 | 4 |
| 1D Full-Mesh + Clos | 2 | 2 | 4 |
| 2D Full-Mesh + Clos | 2 | 2 | 4 |
| GB200 NVL72 缩放实例 | 2 | 2 | 4 |
| 合计 | 8 | 8 | 16 |

每种“拓扑 × 算子”组合设置一个标准任务和一个复杂任务，即标准任务 8 个、复杂任务 8 个。16 个实例等权计分，每类拓扑占正式集的 25%，每类算子占正式集的 50%。

| 类型 | 用途 | 典型特征 |
| --- | --- | --- |
| 公开调试用例（Debug） | 验证镜像、协议和基本正确性，不计入最终排名 | 另行发布完整任务输入、配套拓扑和调试说明 |
| 标准任务（Standard） | 纳入正式集，按第 8 节计分 | 数据量、切分和轮数约束适中，考察基本正确性及分层调度能力 |
| 复杂任务（Hard） | 纳入正式集，与标准任务等权计分 | 更大的数据量、不同切分参数或轮数约束，考察共享资源编排和搜索能力 |

当前用例设计沿用专家资料包的四类输入拓扑：前三类各 128 个 rank，第四类 144 个 rank；各实例通过任务的数据量、split 和轮数上限形成差异。参赛者应从实际下发的任务和拓扑读取参数，不能依赖实例 ID、拓扑名称或公开样例输出固定答案。具体正式用例文件由组委会保存在评测侧，不随参赛者资料包公开。

参赛者上传 Agent 镜像后，服务器按统一测试集自动下发任务、调用 Agent 并校验提交结果，将 solution、Replay 报告、平台求解计时与状态、平台调用统计保存到规定路径，供后续汇总评分和复核。镜像接口、结果目录和文件格式以开发规范及冻结公告为准；参赛者无需在 solution 中增加自报求解时间或评分字段。

接口返回 `success` 只表示 Agent 完成了响应，不表示调度方案通过判题。缺失结果、无法解析、任务/实例不匹配或目标未完成，均按对应实例失败处理，其余实例继续评测，正式评分分母保持 16。失败和超时实例的模型消耗仍纳入本次正式评测的 Token 统计。

每个实例的模型调用配额、Replay 配额、并发上限、求解时间满分阈值和墙钟截止时间以赛前冻结公告为准。调用配额耗尽后，Agent 仍须在截止时间内返回完整可行方案；配额耗尽不延长截止时间。未按时完整提交、提交无效或求解超时，该实例三项得分均为 0，其余实例继续评测。

所有队伍使用相同的冻结用例、资源限制、服务条件和 Replay 版本。允许在限额内进行搜索和并行探索，但禁止使用额外未授权算力；模型调用和 Replay 的硬配额继续执行，不能因 Token 不计分而无限调用。每次实例下发前清理上一次求解的任务状态、临时候选和后台任务；当前实例的任务及拓扑只在计时开始后下发。不得在健康检查、容器启动或实例间隙预先求解隐藏任务，也不得跨实例复用隐藏任务答案。

## 8. 评分维度

本赛题的自动打榜总分为 **100 分**，由方案正确率、通信性能和 Agent 求解时间三项组成。正式集的 16 个实例等权计分，全部纳入分母。该设计同时评价“是否解对”“生成的通信方案是否高效”和“Agent 是否能在有限时间内完成求解”。

| 评分项 | 满分 | 依据 |
| --- | ---: | --- |
| 方案正确率 | 30 | 平台对按时提交的方案进行协议、通信约束及算子目标校验 |
| 通信性能 | 40 | 官方 Replay 耗时与各实例固定基线、标准下界的比较 |
| Agent 求解时间 | 30 | 平台记录的求解墙钟时间，与各实例冻结时间阈值比较 |
| 合计 | 100 | 三项均由平台记录和独立判题结果计算 |

Token 消耗和方案设计专家评价留待后期统一评议，不计入本次自动打榜总分，也不用于自动打破同分。平台继续留存真实调用统计、策略说明及运行记录；后期评议的用途和规则另行公告。本节不预设额外加分或专家评分权重。

### 8.1 方案正确率（30 分）

设实例 `i` 的通过标记为 `v_i`：平台在截止时间内完整收到最终方案，提交结果可解析、与当前任务一致、满足全部硬约束、成功回放并完成算子目标时，`v_i = 1`；否则 `v_i = 0`。错误、缺失、超时或只完成部分目标均记为失败，不按局部完成比例给分。Replay 可在接收截止时间后执行，是否按时以平台完整接收响应的时刻为准。

```text
C = sum(v_i), i = 1..16
正确率分 = 30 × C / 16
```

每通过一个实例获得 `30/16 = 1.875` 分。成绩报告同时列出四类拓扑各自的通过数（满额 4）和两类算子的通过数（满额 8）。失败实例的通信性能和求解时间贡献也均为 0，快速返回错误结果不得分。

### 8.2 通信性能（40 分）

每个实例独立归一化，避免不同数据量和拓扑的绝对耗时直接相加影响公平性。设 `T_i` 为参赛方案的官方 Replay 总耗时，`UB_base_i` 为组委会固定基线方案的 Replay 总耗时，`LB_i` 为组委会统一确定的标准下界，时间单位均为微秒。

`UB_base_i`、`T_i` 和 `LB_i` 均描述通信方案的模型耗时，与 Agent 花了多少秒生成该方案无关；Agent 求解耗时单独按第 8.3 节评分。

```text
通过实例：p_i = clamp((UB_base_i - T_i) / (UB_base_i - LB_i), 0, 1)
失败实例：p_i = 0
性能分 = 40 × sum(p_i) / 16
```

`clamp(x, 0, 1)` 表示将结果限制在 0 到 1 之间。方案达到基线时间时该实例性能分为 0；越接近标准下界，得分越高；达到或优于标准下界时取得该实例性能满分 `40/16 = 2.5` 分。慢于基线的合法方案仍可获得正确率分，但该实例性能分为 0。失败实例保留在分母 16 中，不能仅对成功实例取平均。

基线方案必须满足对应任务约束并通过统一 Replay；各实例应满足 `0 < LB_i < UB_base_i`，在正式评测前完成标定并冻结。16 个实例须全部具备有效标定值；任一实例缺失标定值、数值不满足条件或与冻结的任务、拓扑、Replay 版本不一致时，正式评分暂不启动，不能删去该实例缩小分母，也不能临时从参赛方案推算基线或下界。标准下界由组委会提供，参赛者无需计算或提交下界分析。参赛者自报 metrics 不用于替代官方 Replay 结果。

成绩报告同时列出四类拓扑的 `p_i` 均值（各 4 例）和两类算子的 `p_i` 均值（各 8 例），失败实例均按 0 计入。

### 8.3 Agent 求解时间（30 分）

设 `t_i` 为第 6.2 节定义的平台实测求解时间。每个实例设两个固定参数，单位均为秒：

| 参数 | 含义 |
| --- | --- |
| `t_good_i` | 求解时间满分阈值；正确且在该时间内返回最终方案，获得本实例时间满分 |
| `t_limit_i` | 求解截止时间；超过该时间才完整返回，或未返回，均按超时失败处理 |

两个参数须满足 `0 < t_good_i < t_limit_i`。组委会在统一服务器、计算资源、模型与 Replay 服务条件下，用独立参考实现实测并逐例标定；在正式打榜前冻结并公告，并在任务下发时提供对应限制。满分阈值应体现有效构造可行方案所需的合理时间，并与截止时间留出明显区间，避免大部分高耗时搜索仍落在满分区间。阈值不得根据当次参赛队伍的最快或最慢结果临时确定。

```text
通过实例：q_i = clamp((t_limit_i - t_i) / (t_limit_i - t_good_i), 0, 1)
失败实例：q_i = 0
求解时间分 = 30 × sum(q_i) / 16
```

正确且 `t_i ≤ t_good_i` 时，`q_i = 1`；在满分阈值与截止时间之间，时间得分线性下降。恰在截止时间完整收到且通过判题的方案仍可获得正确率和通信性能分，但时间分为 0；超过截止时间则三项均为 0。每个实例的时间满分为 `30/16 = 1.875` 分。所有实例均保留在分母中，不能只对成功实例计算平均耗时后评分。

例如，仅为说明公式，假设某实例 `t_good_i = 10 秒`、`t_limit_i = 60 秒`：正确方案在 10 秒以内返回，时间贡献为 1.875 分；35 秒返回为 0.9375 分；60 秒返回为 0 分；超过 60 秒则该实例全部得分为 0。上述数字不是正式阈值，正式参数以冻结公告为准。

求解时间分以平台记录为唯一依据。参赛者不能通过先发送空响应、声明完成后继续求解、只提交首个候选的时间，或将求解工作转移到计时区间外获得时间奖励。搜索算法不限；在相同资源内更快找到高质量可行解，可以同时获得通信性能分和求解时间分。

### 8.4 自动打榜总分与并列规则

```text
实例贡献 s_i = (30 × v_i + 40 × p_i + 30 × q_i) / 16
自动打榜总分 S = sum(s_i)，满分 100
             = 正确率分 + 通信性能分 + Agent 求解时间分
```

每个实例最高贡献 6.25 分；四类拓扑各占总分的 25%，两类算子各占总分的 50%。平台报告应展示三项分数，以及每例的通过状态、失败原因、Replay 耗时、平台求解时间、时间阈值和分项贡献。

自动榜按未四舍五入的总分降序排列；展示保留两位小数，不能因展示值相同就判定并列。未四舍五入的总分相同时暂列并列，不再以 Token 消耗、专家评价或其他指标自动调整先后。Token 及方案设计材料供后期统一评议，该阶段与本节自动打榜分开。

### 8.5 数据完整性与计分前提

正式自动评分需要全部 16 个实例的通信性能标定、求解时间阈值，以及平台对各实例的提交状态和计时记录。参数须绑定冻结的任务、拓扑、Replay 版本和评测环境；任一实例的必需标定未冻结、参数不合法或版本不一致时，仅提供已有诊断，不生成正式总分和排名。

平台已明确记录的失败、未提交或超时，按该实例三项 0 分处理；平台计时缺失、记录损坏或基础设施故障不直接视为参赛者失败，应标记待核实并依统一规则处理，不能默认按 0 秒给满分，也不能通过删除实例缩小分母。任一队伍的必要评测数据尚未齐备时，不生成本次完整统一排名。

仅提供 solution 文件时，可以验证正确性并计算 Replay 性能，但不能由文件内容推算 Agent 求解时间或完整 100 分。Token 统计和专家评价不属于本次自动总分的前置条件；未收齐时单独标记待补齐，供后期评议使用。演示或调试的模拟计时、标定和报告须明确标识，不用于正式排名。

## 附录：调度搜索方法示例

以下内容保留 v3 中的出题思路，用于帮助参赛者理解为什么需要“搜索—Replay—复盘”闭环。它不是固定答案，也不代表任何正式实例的基线参数。

### A.1 三个可并行探索的方向

Agent 可以围绕同一任务同时生成多个候选方向，每个方向独立构造方案、调用 Replay 并回写证据：

| 搜索方向                    | 关注点                        | 可能得到的结论                                  |
| ----------------------- | -------------------------- | ---------------------------------------- |
| `hierarchical_baseline` | 按拓扑层级做递归加倍或分层树             | 易于保证正确，但可能只使用一个带宽层，形成串行瓶颈                |
| `radix_or_mesh`         | radix-`k`、AlltoAll、行列/分维交换 | 可以减少轮数，但必须检查高 radix 是否导致共享 Clos 或跨柜链路串行化 |
| `tier_pipeline`         | 把局部 Mesh、汇聚层和跨域链路放入不同流水阶段  | 通过带宽池重叠减少空闲时间，重点是字节分区和到达时序               |

一次模型调用只能给出一个候选，不能证明候选可行或性能最优。候选必须经过 Replay，失败原因和逐轮计时应成为下一轮搜索的输入。

### A.2 推荐的收敛闭环

```text
hierarchical_baseline 建立可行基线
        ↓
radix_or_mesh 验证减少轮次是否有效
        ↓
tier_pipeline 尝试跨层重叠、分片和路径平衡
        ↓
Replay 对每轮字节、共享资源和总时间进行验证
        ↓
保留最好可行方案，并根据失败证据调整下一轮候选
```

应同时记录候选的正确性状态、轮数、各轮耗时、总耗时和使用的共享资源。只压缩轮数而没有改善关键资源瓶颈的方案，可能比基线更慢；只追求局部链路满载而违反持有性、路径或规约贡献约束的方案，不能获得性能分。

### A.3 AllGather 与 AllReduce 的检查重点

- **AllGather**：为每个逻辑分片维护“来源—当前持有 rank—已接收目标”的集合，确保每个目标只接收一次，并优先把跨域字节安排到能产生更多后续分发价值的路径上。
- **AllReduce**：为每个规约分片维护贡献者集合和当前规约位置。ReduceScatter 阶段不得重复计算同一贡献，AllGather 阶段只能复制已经完成规约的分片。
- **共享资源**：不能只检查端点带宽；共享有向边，以及输入明确声明的 L1、L2、NVSwitch、Leaf、Spine 或其他联合容量上的并发传输，必须按对应边或资源定义合并计费。
- **跨轮状态**：只能把数据落到目标 rank 后带入下一轮，交换机只负责当前轮逐跳转发。
